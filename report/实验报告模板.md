## 三、实验整体逻辑分析

### 3.1 逻辑主线

本实验的核心是先确定“哪些物理页能够使用”，再解决“如何分配和回收这些页”。设备树提供 DRAM 的起点和大小，但其中并非全部空间都能作为空闲页：固件、内核镜像以及内核维护的页描述符都占用内存，需要先保留。

`page_init()` 根据设备树信息和链接符号 `end` 建立 `pages[]`，初始化所有页的管理状态，再将剩余完整页面交给当前分配器。它负责初始布局，不负责决定分配时选择哪一个空闲块。不同分配器经由统一的 `pmm_manager` 接口接入。

```text
内核读取并解析 DTB
  └─ pmm_init()
       ├─ init_pmm_manager()         选择并初始化分配器
       ├─ page_init()                建立物理页描述符布局
       │    └─ init_memmap()         登记合法的初始空闲页
       └─ check_alloc_page()         调用当前分配器的自检

后续 alloc_pages()/free_pages()
  └─ 转发至当前 pmm_manager 的实现
```

地址翻译与页面分配是相关但不同的机制：页表决定虚拟地址如何映射到物理地址，分配器管理可用物理页。本框架在启动汇编中已经建立 Sv39 映射，不能把 `page_init()` 写成开启分页的函数。双 GDB 分支任务是在这一基础上观察 uCore 访存和 QEMU 模拟地址翻译的过程。

### 3.2 功能之间的依赖

1. 解析设备树，为内存布局计算提供物理范围。
2. 初始化当前管理器，使它能够接收初始空闲区。
3. 执行 `page_init()`，保留已占用区域并登记可分配页面。
4. 通过分配器接口申请和回收页面，验证布局与管理状态。
5. 使用 GDB 检查关键状态，再通过双 GDB 调试进一步观察页表和 TLB。

当前整合代码在 `init_pmm_manager()` 中选择 `buddy_pmm_manager`。A 登记的连续空闲区由 C 按物理页号对齐拆成不同阶的块，后续分配、释放与自检均经过同一组公共接口。C 的实现和测试见 4.3 节，B 的算法分析与验证由本人补充。选择 Buddy 时的自检结果和 Best-Fit 配置下的评分需要分别理解，不能混用。

#### 4.1.1 模块功能描述

**需要实现的函数：**

```c
static void page_init(void);
```

`page_init()` 根据设备树提供的物理内存范围建立 `struct Page` 描述符数组，并把排除 OpenSBI、内核镜像和描述符数组后的完整空闲页面注册给当前 `pmm_manager`。成功完成后，以下全局状态必须有效：

- `va_pa_offset`：内核虚拟地址与物理地址之间的线性映射偏移；
- `npage`：可管理物理地址上界对应的物理页号；
- `pages`：物理页描述符数组的内核虚拟地址；
- 分配器的初始空闲区：从描述符数组结束后的第一个完整页面开始，到可管理物理内存末尾结束。

#### 4.1.2 功能 Spec

**前置条件：**

1. DTB 初始化已经完成，`get_memory_base()` 和 `get_memory_size()` 可用；
2. 链接符号 `end` 指向内核镜像末尾；
3. 当前 `pmm_manager` 已选择并完成自身初始化；
4. 地址转换、页面大小和页面状态宏可用。

**后置条件：**

1. DTB 返回的内存范围有效，否则通过 `panic()` 终止；
2. `va_pa_offset == PHYSICAL_MEMORY_OFFSET`；
3. 可管理上界不超过框架允许的物理内存上界，并按页向下对齐；
4. `npage` 与可管理物理内存末端相符；
5. `pages` 位于 `ROUNDUP(end, PGSIZE)`；
6. 所有页描述符先初始化为保留状态且引用计数为 0；
7. 内核镜像及 `pages[]` 自身占用的页面保持保留；
8. 只有描述符数组之后的完整页面进入空闲区；
9. 没有完整空闲页时不得调用 `init_memmap()`；
10. 输出实际探测到的物理内存范围。

#### 4.1.4 核心实现逻辑

实现按以下关系计算内存布局：

```text
mem_base    = get_memory_base()
mem_end     = mem_base + get_memory_size()
managed_end = min(mem_end, PHYSICAL_MEMORY_END)，随后按页向下对齐
npage       = PPN(managed_end)
pages       = ROUNDUP(end, PGSIZE)
pages_end   = pages + (npage - nbase) * sizeof(struct Page)
free_begin  = ROUNDUP(PADDR(pages_end), PGSIZE)
free_end    = managed_end
```

`pages[]` 为从 `nbase` 到 `npage` 范围内的每个物理页提供描述符。初始化时先把所有描述符设置为 reserved，并清空 `property` 和引用计数。这种“先全部保留、再释放合法区间”的方法能够避免遗漏内核或管理数据占用的页面。

当 `free_begin < free_end` 时，通过：

```c
init_memmap(pa2page(free_begin),
            (free_end - free_begin) / PGSIZE);
```

把完整空闲页交给当前分配器。`page_init()` 不直接决定使用 First-Fit、Best-Fit 还是 Buddy System，从而保持探测逻辑与分配策略解耦。

#### 4.1.5 关键检查与实现边界

| 检查位置 | 当前源码的处理 |
|----------|----------------|
| DTB 内存范围 | 起点或大小为零、末端加法回绕时 `panic()` |
| 平台内存起点 | 当前实现要求 `mem_base == DRAM_BASE`，否则终止 |
| 管理上界 | 不超过 `PHYSICAL_MEMORY_END`，并按页向下对齐 |
| 物理页范围 | 检查 `npage > nbase` |
| 描述符数量与地址计算 | 检查数量乘法和地址加法溢出 |
| 页面初始状态 | 逐页清 `flags`、`property`、引用计数，再设置 `PG_reserved` |
| 空闲区登记 | `free_begin < free_end` 时才调用 `init_memmap()` |

`npage` 是管理末端对应的物理页号，不是 `pages[]` 的元素个数。数组实际元素数为 `npage - nbase`，物理页号为 `ppn` 的页对应 `pages[ppn - nbase]`。混淆这两者会导致数组大小和描述符索引计算错误。

当前实现针对框架的单段 DRAM 布局；本报告不将它描述为已经支持任意起点、多个离散内存区或内存热插拔。已有截图验证了正常实验配置的布局，未逐项运行零大小、溢出和无空闲完整页等异常输入，因此不宣称已经完成全部异常路径的动态测试。

### 4.3 C：Buddy System 分配器与测试

**负责人：** 2413551-李睿。

**源码：** [`buddy_pmm.c`](../code/kern/mm/buddy_pmm.c)、[`buddy_pmm.h`](../code/kern/mm/buddy_pmm.h)，通过 [`pmm.c`](../code/kern/mm/pmm.c) 中的 `pmm_manager` 接入，保留学号 `2413551` 注释。

#### 4.3.1 需求分析与功能 Spec

Buddy 将连续物理页组织成大小为 2 的幂的块。申请时选择能够覆盖请求的最小阶，必要时拆分更大的空闲块；释放时只与同阶的真实伙伴合并，而不是合并任意相邻块。我先明确块大小、物理对齐、块头状态与空闲计数之间的关系，再分别整理实现和测试的提示词。

本模块沿用现有 `pmm_manager` 接口：

| 接口 | 作用与约定 |
|------|------------|
| `buddy_init()` | 初始化各阶空闲链表、块数和总空闲页数 |
| `buddy_init_memmap(base, n)` | 接收已经由 A 排除保留区域的连续空闲区，将其拆成满足物理对齐要求的块 |
| `buddy_alloc_pages(n)` | 对正数请求向上取整，返回实际分配块的首页；没有合适块时返回 `NULL` |
| `buddy_free_pages(base, n)` | 对合法的已分配块，按块头保存的实际容量逐页清理并回收，再尝试向上合并 |
| `buddy_nr_free_pages()` | 返回全部空闲块所含的总页数 |
| `buddy_check()` | 执行测试与不变量检查，通过后输出成功信息 |

**前置条件：** `pages[]`、`nbase`、`npage` 和地址转换接口已就绪；初始登记区间中的页为 reserved；正常分配请求满足 `n > 0`；释放使用原分配块的首页，且不篡改分配器保留的块容量元数据。

**后置条件：** 空闲块容量为 2 的幂且起始物理页号按容量对齐；块头状态与所属阶一致；空闲页总数按实际容量增减；分裂和合并本身不增加或减少空闲总容量；无合适块的分配在修改链表前返回 `NULL`。

#### 4.3.2 数据结构与元数据约定

实现设置 `MAX_ORDER = 20`，有效阶为 0—19；第 `k` 阶块含 `1UL << k` 个连续物理页。`free_area[k]` 管理该阶的双向空闲链表，其 `nr_free` 记录**块数**；独立变量 `buddy_nr_free` 记录**总空闲页数**，两者单位不同。

```text
第 k 阶块容量 = 2^k 页
总空闲页数 = Σ（第 k 阶空闲块数 × 2^k）
```

块首页的 `property` 保存实际块容量，不是阶数。`PG_property` 表示该页是空闲块首页；分配后清除此标志，但保留块容量，以便释放时恢复阶数。例如申请 3 页实际取得 4 页，`property == 4`，总空闲页数减少 4；申请 5 页实际取得 8 页。由此产生的剩余容量属于块内的内部碎片。

伙伴计算使用绝对物理页号：

```c
ppn_t ppn = page2ppn(p) ^ (1UL << order);
if (ppn < nbase || ppn >= npage) {
    return NULL;
}
return &pages[ppn - nbase];
```

因此，块对齐要求是物理页号的低 `order` 位为 0，不能直接用 `Page` 数组下标进行异或。两个块即使地址相邻，也只有满足上述伙伴关系、阶数相同且伙伴确实空闲，才可以合并。

#### 4.3.3 初始化、分配与释放

**初始空闲区拆分。** `buddy_init_memmap()` 先逐页清空状态、`property` 和引用计数，再从区间起点开始，选择不超过剩余长度、同时满足当前物理地址对齐的最大阶。将该块登记到对应链表后，继续处理余下区间。初始区间不必自身就是一个 2 的幂块；当前工程由 A 提供一段合法连续区域。

**分配与分裂。** `buddy_order_for(n)` 求覆盖请求的最小阶。分配器从该阶向高阶寻找非空链表，摘取一个块后逐级二分，把后半块挂入下一阶，继续保留前半块，直到达到目标阶。最后清除返回块首页的 `PG_property`，保存实际容量，并按该容量扣减 `buddy_nr_free`。若请求超过总空闲页数，或各候选阶均无可用块，则返回 `NULL`。

**释放与合并。** 释放时从 `base->property` 恢复容量和阶，检查容量为 2 的幂、不小于传入的 `n`，并满足物理对齐。逐页清理整个实际块后，总空闲页数只增加一次。随后利用异或求伙伴，检查伙伴范围、空闲块头标志和容量；符合条件时从原阶链表摘除伙伴，取低地址作为新首页并向上一阶继续检查。最终将合并块挂入对应链表。

这里的 `free_pages(p, 3)` 对应归还先前申请 3 页而取得的完整 4 页块，并非从任意块中切出 3 页释放。混合测试中“部分释放”指释放若干已分配对象中的一个。本实现依赖合法的整块释放调用，不宣称支持任意子区间释放或完整的非法释放检测。

## 1. order 与块
- order=k 的块包含 2^k 个连续物理页。

- 将整个范围贪心分解为若干互不重叠、各自满足对齐的 2 的幂块；所有块容量之和恰好为 n，不丢头尾页，不把范围外页面加入。

## 4. 分配（buddy_alloc_pages）
前置条件：n > 0。
失败情况：不存在足够容量的块时返回 NULL，且不得改变任何空闲结构、Page 状态或 nr_free。
成功情况：
- 计算覆盖 n 的最小 order；优先从对应 order 取；该阶为空则从更高阶逐级二分，每次分裂出的另一半（buddy）挂入正确的下一阶空闲结构。

- nr_free 按实际占用块容量（1<<order）减少；返回范围不与其它已分配块重叠。
- 非 2 的幂请求（如 3、5 页）按向上取整处理（3 页占用 4 页），统计与释放均按实际块容量。

## 5. 释放（buddy_free_pages）
前置条件：base 是此前成功分配块的首地址；实现用 base->property 反推实际 order。
约束：用 assert 约束非法释放（与 First-Fit 一致）——释放的页应满足 !PageReserved 且 !PageProperty；base 的 property 应为 2 的幂且块对齐，否则 assert 失败。

- 恢复该块空闲状态（SetPageProperty，property=1<<order）。
- 计算同阶伙伴 page2ppn(base) ^ (1<<order)；仅当伙伴位于管理范围（page2ppn < npage）、当前空闲（PageProperty 为真）、order 相同、且地址关系正确时才合并。
- 每次合并产生更高一阶块，重复直到伙伴不可合并或达到 MAX_ORDER；非伙伴块即使物理相邻也不合并。
- nr_free 只增加本次释放块的容量，合并过程不重复增加 nr_free。

## 6. 空闲页统计
- buddy_nr_free_pages() 返回实际空闲页总数，必须等于所有 order 空闲块容量之和。
- 分裂与合并不改变空闲页总数；分配与释放按实际块容量增减计数。

#### 4.3.5 已实现的测试及有效性

`buddy_check_invariant()` 遍历各阶链表，检查每个节点的 `PG_property`、容量和物理对齐，并累加所有块容量，与 `buddy_nr_free` 比较。`buddy_check()` 在测试前后执行该检查，并确认总空闲页数恢复；每个测试也将申请到的块全部归还。

| 测试函数 | 实际执行的操作与断言 | 能检验的问题 |
|----------|----------------------|--------------|
| `buddy_test_alloc_sizes` | 逐项申请并释放 1、2、3、4、5、8、16 页；检查非空、块头标志、容量为 2 的幂且覆盖请求、物理对齐、容量计数和归还后的计数恢复 | 不同请求大小、返回块元数据、对齐与分配回收的基本一致性 |
| `buddy_test_roundup` | 明确断言 3 页请求取得 4 页、5 页请求取得 8 页，并按 4、8 校验计数 | 防止按请求页数而非实际容量记账 |
| `buddy_test_split` | 连续申请两个单页，逐步检查计数和不变量，再全部归还 | 检查单页分配及空闲块状态；当低阶链表为空时会经过高阶分裂路径 |
| `buddy_test_merge` | 连续申请两个单页并依次释放，检查各步计数、最终恢复及不变量 | 检查释放后的容量与元数据一致性，发现部分回收错误 |
| `buddy_test_mixed` | 申请 1、3、8、1 页，归还 3 页请求对应的完整块，再申请 2 页，最终全部释放 | 检查混合大小和交错回收中的实际容量计数及空闲结构一致性 |
| `buddy_test_fail` | 申请当前空闲总数加 1 页，以及 `2^20 + 1` 页；断言 `NULL`、总数不变、不变量成立 | 检查明显超量请求的失败返回及容量状态保持 |

这些断言分别观察返回结果、块头元数据、对齐和全局容量，能够比单一成功输出提供更具体的检查。测试完成后的总容量恢复可以检出部分漏还和记账错误，但不等于各阶链表的节点顺序或块形态与测试前逐项相同。

**设计目标与当前覆盖的区别：** 第二份提示词提出了强制构造分裂、明确验证伙伴合并和非伙伴不合并，以及保存状态快照等要求。现有代码采用分配后完整归还来恢复容量，没有保存并还原整套链表快照；分裂测试未强制每次都从高阶开始，合并测试也未显式断言两个返回块构成伙伴及合并后的指定阶块。因此，这些用例已运行通过，但不能据此写成“所有分裂、合并边界均已独立覆盖”。

另外，不变量函数未逐阶核对链表节点数与 `free_area[k].nr_free`，也未全面检查块之间重复或重叠；混合测试是固定序列，不是随机压力测试。源码中的非法释放场景只有说明性注释，没有实际执行，现有断言也不构成完整的所有权检测。后续若加强测试，可补充确定性的伙伴构造、非伙伴不合并断言和每阶计数核对；这些属于改进方向，不写成已提交成果。

#### 4.3.6 实际问题与修复：释放时遗漏块内页面

此前释放循环只递增计数变量，没有推进页面指针，结果会反复处理块首页，遗漏同一实际块内其余页面的状态和引用计数。空闲页总数仍可能恢复，因此只观察总容量不能发现这类逐页清理错误。

当前实现已经改为推进 `p`，遍历整个实际容量：

```c
struct Page *p = base;
for (; p != base + size; p++) {
    assert(!PageReserved(p) && !PageProperty(p));
    p->flags = 0;
    set_page_ref(p, 0);
}
```

修复范围是逐页清理循环，分配容量、伙伴计算和整块合并约定保持一致。修复后普通 Buddy 自检通过；另外在隔离副本中，对 2、3、5、8、16 页请求所得块的全部页面预先设置非零引用计数和测试标志，释放后逐页检查清理结果，也已通过。将旧循环放回同一专项验证时会触发引用计数未清零的断言。该专项验证用于核验修复，不属于仓库中现有六个自检函数的覆盖。

这一问题说明，测试不仅要检查“空闲容量是否恢复”，还应检查“每个被回收页面的局部状态是否恢复”。现有普通测试未在内部页面预设非零引用计数，因此不能单靠其成功输出证明该缺陷从未存在。

#### 4.3.7 算法特点与本次实现边界

Buddy 通过固定阶链表和伙伴地址计算组织分配与回收，避免将任意相邻块都当作可合并伙伴。代价是非 2 的幂请求需要向上取整，可能产生内部碎片；总空闲页数充足也不必然存在满足目标阶的连续块。

当前实现面向实验中的单段物理内存和合法整块分配、释放接口，未扩展并发同步、NUMA、热插拔或小对象缓存。释放还需要逐页清理状态，不能只按“最多合并若干阶”就把整个释放过程描述为与块内页数无关。

### 4.5 A：硬件可用物理内存范围思考题

**问题：如果 OS 无法提前知道硬件的可用物理内存范围，如何获取？**

内核应读取固件或启动程序提供的内存地图，而不是假定内存大小固定。本实验由设备树的内存节点提供 DRAM 起点和长度，启动链把 DTB 交给内核，解析结果经 `get_memory_base()`、`get_memory_size()` 使用。其他平台也可由 BIOS 内存地图或 UEFI memory map 等接口提供可用与保留区域。

获得 RAM 范围后，内核仍需扣除固件、内核镜像、页表、管理结构和其他保留区，再按页对齐登记可用区域。不能通过任意读写所有物理地址来替代可靠的内存地图，因为访问可能触发异常或影响 MMIO 设备。

本实现按照当前框架的一段 DRAM 管理，若要支持多个离散可用区，还需要逐段处理范围与保留区域；这一扩展未在本次代码中实现。

## 六、实验总结与收获（A、C 部分）

### 6.1 重要知识点及其与 OS 原理的联系

| 知识点 | 本实验中的体现 | 与 OS 原理的联系及边界 |
|--------|----------------|------------------------|
| 物理内存地图 | 从 DTB 获取 DRAM 起点和长度 | 平台提供原始范围，内核进一步排除已占用区域；本实现不是通用多区域探测器 |
| 页框管理与元数据 | 每个页框对应一个 `struct Page` | 描述符存放管理状态，并非页框内容本身；管理元数据同样占用物理内存 |
| 地址空间转换 | `PADDR`、物理页号、`pages[ppn-nbase]` | 线性映射的算术转换和硬件页表翻译需要区分；不能混用地址与数组索引 |
| 对齐与保留区 | 上界向下对齐，空闲起点向上对齐 | 只登记完整页面，避免将内核或描述符尾部所在页重复分配 |
| 接口与策略分离 | `page_init()` 通过 `init_memmap()` 接入分配器 | 内存布局初始化不决定具体分配策略，统一接口降低模块耦合 |
| Buddy 分级管理 | 各阶链表、物理页号对齐、异或求伙伴、逐级分裂与合并 | 以规则块结构管理连续页；不能把任意相邻块当作伙伴 |
| 内部碎片与容量统计 | 3 页请求占 4 页、5 页请求占 8 页 | 请求大小与实际保留容量不同，计数和回收必须采用一致单位 |
| 不变量与局部状态 | 空闲容量求和、块头元数据检查、释放时逐页清理 | 总量守恒有助于检查记账，但不能替代对每页状态及具体合并行为的验证 |
| 页表与 TLB | 启动映射、根页表地址及后续调试目标 | 用于虚拟地址翻译；当前客体状态检查尚不等于完成软件 TLB 与页表遍历的实测 |

### 6.2 OS 原理中重要但本部分尚未覆盖的内容

1. 用户进程独立地址空间的建立、切换和销毁。
2. 缺页异常、按需分页、页面置换和交换。
3. 写时复制、共享内存与文件映射。
4. 多核页表更新、TLB 一致性和 TLB shootdown。
5. NUMA、内存热插拔、并发分配器同步与复杂保留区域处理。

### 6.3 AI 协作开发的实际经验

**先理解模块职责，再设计提示词。** 我先梳理 `page_init()` 与 DTB、链接符号、全局变量及管理器初始化顺序的关系，明确它负责页级内存布局而非分配策略，再把目标、依赖、责任和检查条件写入提示词。AI 根据这些需求生成实现代码，我结合源码与运行结果分析是否符合预期。

**把理解转化为可核验条件。** 理解页描述符也会占用物理内存后，我在提示词中要求保留描述符数组所在区域；理解页面分配以整页为单位后，我明确空闲区两端的对齐条件。通过 GDB 比较保留标志、空闲块大小和计数，可以进一步检验这些要求是否落实。

**区分环境问题、算法结果与任务完成状态。** 编译失败可能来自尚未完成的其他源文件，启动异常也不能直接推断为本函数错误。隔离副本可以验证 A，但报告必须说明辅助改动；客体 GDB 检查通过，也不能替代双 GDB 分支任务。

**保留真实结果及其上下文。** 截图中第二项 Best-Fit 失败与 A 阶段使用 First-Fit 的配置有关，应完整保留并解释，不能裁掉失败行后宣称全部通过。尚未完成的双 GDB 调试仍保留待补充状态。

**C：从数据约定出发设计实现与测试。** 理解 `property` 保存实际容量、`PG_property` 标识空闲块首页后，将它们与物理对齐、伙伴关系和计数规则一起写入提示词，使生成代码能够遵循统一接口。实现提示词与测试提示词分开整理，有助于把“算法能运行”和“哪些性质得到检查”分别说明。

**C：检查提示词要求是否落实到断言。** 释放循环的修复说明，即使总容量恢复，内部页面状态仍可能错误；分裂和合并测试的分析也说明，测试函数名称不能代替对具体路径的断言。报告按实际代码说明覆盖范围，并将尚未实现的加强用例列为改进方向。
